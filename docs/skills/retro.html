retro — fix the setup, not just the session

A session's mistakes repeat until something in the setup changes: a memory the next session reads, a skill step, a rule, a hook. This skill finds the moments that cost time and proposes the smallest durable change for each.

Arguments

ArgumentMeaning
(none)review the current conversation
<transcript path>review a saved session transcript instead (for Claude Code, a .jsonl file under ~/.claude/projects/<project>/)
--focus=<topic>look only at one area, such as git, tests or a named skill

Project settings

Reads the project profile (AI_TOOLBOX_PROFILE, else <project root>/.ai-toolbox/profile.yml): docs.memory_dir is where lessons live. Without it, use the tool's own memory folder if one exists, or say there is none.

Steps

1. Find the friction

Go through the session in order and list each moment that cost a turn or more. For a transcript file, grep for the signals instead of reading it whole.

SignalExample
User correction"no, that's not what I meant", a rejected tool call, a re-asked question
Blocked actionpermission denied, a hook blocked a command, a sandbox refusal
Retrythe same command or edit tried more than once
Wrong claimsomething stated as fact, then shown wrong
Missing contexta fact the session had to rediscover that an earlier session already knew
Skill mismatcha skill that didn't trigger, triggered wrongly, or whose step didn't fit

For each: what happened (a short quote or the command), turns lost, and the root cause in one line.

Done when: each friction moment has a cause, or the session had none worth fixing (say so and stop).

2. Pick the smallest durable fix

Match each cause to where a fix would have prevented it:

CauseFix lives in
A fact about the user, project or team the session lackedmemory entry
A skill step that was missing, wrong or ambiguousthat skill's SKILL.md
A convention the code follows but nothing statesproject rule file (CLAUDE.md, AGENTS.md, .claude/rules/)
A check that prose kept failing to enforcehook
A safe command that kept asking for permissionpermission allow-list
A project value a skill had to ask forprofile key

Before proposing a memory entry, grep {memory_dir} for an existing one: update it rather than adding a duplicate. Before proposing a skill edit, read the current step; the fix may belong one step earlier.

Check where the target file is published before putting anything in it. A file in a public or shared repo (a toolbox, a dotfiles backup) gets generic wording only: no employer, product, repository, host, schema, table or column names, and no internal paths. Work-specific facts go to the memory folder or to a file no repo tracks (git -C <dir> check-ignore -v <file> confirms).

Done when: each cause has one proposed fix with its target file.

3. Rank and present

Before the table, re-check each finding's evidence with a command: a claim that something is missing needs a search of the whole repo or plugin, not one folder. Correct or drop any finding that fails the check.

Then leak-check the drafted text of every fix aimed at a public or shared repo: match it against the private leak patterns (AI_TOOLBOX_LEAK_PATTERNS, default ~/.config/ai-toolbox/leak-patterns.txt, one case-insensitive regex per line) and reword any hit. Never print the matched value.

Output the complete table and item descriptions as regular markdown text, then ask the user in plain text which to apply (e.g. "Which of these would you like to apply: all, specific numbers, or none?"). Do NOT use the interactive question modal (AskUserQuestion / ask_question) here so the user can review all details on screen before answering.

4. Apply only what was picked

  • Memory: write or update the entry and its index line.
  • Skills, agents, rules, hooks, permissions: show the diff first and apply after the user confirms that diff; these change how every future session behaves. Right before showing a diff, re-read the target file and run git -C <repo> status --short, git -C <repo> branch --show-current and git -C <repo> log -1 --format='%h %cr' -- <file>. A forked or parallel session may already have made the change, or the repo may be on a branch where it does not apply. If so, report that instead of showing the diff.
  • After applying, run the repo's leak check in every repo you edited (the leak-check skill; in the toolbox, python3 -I tools/leak_check.py). Report findings by file:line only, reword, and re-run until it exits 0 for the files you touched.
  • Report what was applied, and which items were left for later.

Boundaries

Quote only what is needed to show the friction. Leave out secrets, tokens and personal data from the session, colleagues' names from anything written to a shared file, and work-specific names from anything written to a public repo.
